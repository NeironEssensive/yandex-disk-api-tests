# API-автотесты Яндекс Диска

Пример проекта автотестов для [REST API Яндекс Диска](https://yandex.ru/dev/disk-api/doc/ru/):
72 теста на методы **GET, POST, PUT, DELETE** (плюс PATCH) — от позитивных сценариев
до проверок авторизации и конфликтов.

Тестируется реальный API `https://cloud-api.yandex.net`.

## Стек

| Что | Зачем |
|---|---|
| **Java 17** | записи (`record`) под модели ответов, текстовые блоки |
| **JUnit 5** | движок тестов: теги, параметризация, собственное расширение жизненного цикла |
| **REST Assured 5** | HTTP-клиент и проверки ответов |
| **AssertJ** | читаемые ассерты с описанием (`as("...")`) |
| **Jackson** | разбор JSON в модели (snake_case → camelCase, даты) |
| **JSON Schema Validator** | проверка структуры ответа, а не только отдельных полей |
| **Allure 2** | отчёт с шагами, запросами и ответами |
| **Maven** (+ wrapper) | сборка и запуск |
| **GitHub Actions** | прогон на каждый push и pull request |

## Быстрый старт

### 1. Токен

Тесты работают с настоящим Диском, поэтому нужен OAuth-токен. **Используйте отдельный
тестовый аккаунт Яндекса, не личный** — тесты создают и удаляют файлы.

1. Зарегистрируйте тестовый аккаунт Яндекса (или войдите в уже существующий тестовый).
2. Откройте [полигон Яндекс Диска](https://yandex.ru/dev/disk/poligon/) и получите
   OAuth-токен для отладочного приложения.
3. Положите токен в файл `.env` в корне проекта:

```bash
cp .env.example .env
```

```properties
YANDEX_DISK_TOKEN=y0_AgAAAAA...
```

Файл `.env` перечислен в `.gitignore` — в репозиторий он не попадёт. Альтернативы:
переменная окружения `YANDEX_DISK_TOKEN` или параметр `-Dyandex.disk.token=...`.

### 2. Запуск

```bash
./mvnw test
```

Если Maven установлен, можно просто:

```bash
mvn test
```

Полезные варианты запуска:

```bash
mvn test -Dgroups=offline          # только офлайн-тесты: без сети и без токена
mvn test -Dgroups=api              # только тесты против реального API
mvn test -Dtest=CopyMovePostTest   # один класс
mvn test -Dtest=UploadFileTest#uploadsFileByLink   # один тест
mvn test -Dyandex.disk.token=y0_AgAAAAA...         # токен параметром, без .env
```

### 3. Отчёт Allure

```bash
mvn test
mvn allure:serve
```

Отчёт откроется в браузере: шаги, запросы и ответы по каждой проверке.
Значение токена в отчёт не попадает — заголовок `Authorization` маскируется.

## Что проверяется

| Метод | Эндпоинт | Проверки | Класс |
|---|---|---|---|
| GET | `/v1/disk/` | квота непротиворечива, соответствие JSON-схеме, параметр `fields`, 401 без токена и с невалидным токеном | `DiskInfoGetTest` |
| GET | `/v1/disk/resources` | `limit`/`offset`, `sort=-name`, `fields`, соответствие схеме, 404 с телом ошибки | `ResourceListGetTest` |
| GET | `/v1/disk/resources/files`, `/last-uploaded` | плоские списки: только файлы, свежий файл в выдаче | `ResourceListGetTest` |
| GET | `/v1/disk/resources/upload` | временная ссылка, метод `PUT`, `operation_id`; 409 на занятый путь | `UploadFileTest` |
| GET | `/v1/disk/resources/download` | скачанные байты совпадают с загруженными | `UploadFileTest` |
| GET | `/v1/disk/public/resources` | метаданные и содержимое публичного ресурса по `public_key` | `PublishPutTest` |
| GET | `/v1/disk/trash/resources` | удалённый файл найден в Корзине по `origin_path` | `DeleteResourceTest` |
| GET | `/v1/disk/operations/{id}` | ожидание статуса `success` для асинхронных операций | `UploadFileTest`, `CopyMovePostTest` |
| POST | `/v1/disk/resources/copy` | копия создана, содержимое совпадает; 409 без `overwrite`, 201 с ним; непустая папка; 404 на несуществующий источник | `CopyMovePostTest` |
| POST | `/v1/disk/resources/move` | файл переехал, `resource_id` тот же, по старому пути 404; непустая папка | `CopyMovePostTest` |
| POST | `/v1/disk/resources/upload?url=` | 202, асинхронная операция завершается успехом, файл совпадает по MD5 | `UploadFileTest` |
| PUT | `/v1/disk/resources` | 201 и ссылка на метаданные, вложенная папка, 409 на дубль, 409 без родителя, 409 на месте файла | `CreateFolderPutTest` |
| PUT | по ссылке загрузки | 201, размер и MD5 на Диске совпадают с исходными; `overwrite=true` заменяет содержимое | `UploadFileTest` |
| PUT | `/v1/disk/resources/publish`, `/unpublish` | появляются `public_url` и `public_key`, публикация папки, снятие публикации, 404 | `PublishPutTest` |
| PUT | `/v1/disk/trash/resources/restore` | файл восстановлен из Корзины с тем же содержимым | `DeleteResourceTest` |
| DELETE | `/v1/disk/resources` | 204 и файл в Корзине; `permanently=true` не оставляет следов; непустая папка удаляется асинхронно; 404 | `DeleteResourceTest` |
| DELETE | `/v1/disk/trash/resources` | удаление конкретного ресурса из Корзины | `DeleteResourceTest` |
| PATCH | `/v1/disk/resources` | `custom_properties` записываются и перезаписываются; 404; 400 на некорректное тело | `CustomPropertiesPatchTest` |
| — | все методы | каждый метод без токена отвечает 401 с телом ошибки (параметризованный тест) | `UnauthorizedAccessTest` |
| — | без сети | разбор ответов в модели, `_embedded`, даты, неизвестные поля, JSON-схемы, настройки | `JsonMappingOfflineTest` |

Итого 72 теста в 10 классах. Из них **23 выполняются без токена**: 13 офлайн-проверок
и 10 проверок авторизации.

## Структура проекта

```
src/test/java/ru/qa/disk/
├── config/    TestConfig         — настройки: .env, переменные окружения, -D параметры
├── core/      ApiSpec            — спецификации запросов и общая настройка REST Assured
│              AllureRequestFilter — запрос/ответ в отчёт, токен маскируется
│              PlaygroundLifecycle — расширение JUnit: пропуск без токена, песочница на Диске
│              Endpoints, HttpStatus, JsonMapperFactory
├── model/     DiskInfo, Resource, ResourceList, Link, Operation, ApiError, ...
├── api/       DiskInfoApi, ResourcesApi, UploadApi, PublicApi, TrashApi, OperationsApi
├── steps/     DiskSteps          — прикладные шаги: создать, загрузить, дождаться, найти в Корзине
├── util/      Playground, TestData, Await
└── tests/     сами тесты
src/test/resources/
├── application.properties        — значения по умолчанию
├── junit-platform.properties     — настройки движка JUnit
├── fixtures/                     — сохранённые ответы API для офлайн-тестов
└── schemas/                      — JSON-схемы ответов
```

## Принятые решения

**Три слоя вместо одного.** Классы в `api/` только отправляют запросы и возвращают «сырой»
`Response` — они ничего не утверждают, поэтому один и тот же клиент годится и для позитивной
проверки, и для ожидания 409. Утверждения о подготовке данных живут в `steps/`: если упало
создание папки, в отчёте это видно как «не удалось создать папку», а не как NPE в середине
теста. Решение о том, какой код ответа правильный, всегда принимает сам тест.

**Изоляция тестов.** Каждый тест работает в собственной папке
`disk:/qa-autotests/<Класс>.<метод>-<случайный суффикс>` и удаляет её за собой, а вся песочница
удаляется после прогона (расширение JUnit `PlaygroundLifecycle` + `CloseableResource`).
Тесты не зависят от порядка запуска, а на аккаунте не остаётся мусора.

**Токен нигде не светится.** Заголовок `Authorization` внесён в blacklist REST Assured
(поэтому не попадает в консольный лог при падении) и маскируется в своём Allure-фильтре.
Штатный `AllureRestAssured` логирует заголовки как есть — для отчёта, который уезжает
в артефакты CI, это плохая идея.

**Без токена тесты пропускаются, а не падают.** Если токен не задан, классы с тегом `api`
пропускаются с подсказкой, как получить токен, а офлайн-тесты и проверки 401 выполняются.
Свежеклонированный репозиторий даёт осмысленный результат сразу.

**Асинхронные операции.** Операции с непустыми папками и загрузка по URL возвращают 202
и ссылку на операцию. Такие ответы обрабатываются явно: идентификатор операции извлекается
из `href`, статус опрашивается до `success` (`Await` + настройки `async.*`), и только потом
проверяется результат. Где API допускает и 201, и 202, тест принимает оба кода и дожидается
завершения — это свойство API, а не «подгонка» ассерта.

**Тесты идут последовательно.** Прогон использует один аккаунт: Корзина и квота — общее
состояние, а у API есть ограничения на частоту запросов. Настройки для параллельного запуска
описаны в `junit-platform.properties`.

**Корзина не очищается целиком.** Тесты удаляют из Корзины только свои ресурсы: удалять
чужое на живом аккаунте нельзя, даже на тестовом.

**Кодирование URL.** Значения параметров (`path`, `url`) кодирует REST Assured. Наоборот,
для временных ссылок на загрузку и скачивание кодирование отключено: ссылка уже подписана,
и повторное кодирование сломало бы подпись.

## CI

[`.github/workflows/tests.yml`](.github/workflows/tests.yml) запускается на push в `main`,
на pull request и вручную (кнопка **Run workflow** во вкладке Actions). Две джобы:

1. `offline` — тесты без сети и токена, быстрая обратная связь;
2. `api` — тесты против API Диска; токен берётся из секрета `YANDEX_DISK_TOKEN`
   (**Settings → Secrets and variables → Actions**).

Отчёты (`surefire-reports`, `allure-results`) сохраняются как артефакты сборки.
Если секрет не задан, тесты с токеном пропускаются, а проверки авторизации всё равно
выполняются — сборка при этом не падает.

Возможное развитие: публикация Allure-отчёта на GitHub Pages и запуск по расписанию.

## Требования

* JDK 17 или новее (проверялось на JDK 22, компиляция на уровне 17);
* Maven 3.9+ — или `./mvnw`, который скачает нужную версию сам;
* доступ в интернет к `cloud-api.yandex.net`.
